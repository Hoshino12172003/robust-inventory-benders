# Batch-4 CCG 与 Hybrid v7 消融实验报告

## 1. 消融问题

Hybrid v7相对原纯 CCG同时改变了两个因素：每轮完整场景块数量由1个增加到最多4个，并为最严重的未提升场景增加1条Farkas哨兵割。为识别速度改善究竟来自哪一部分，本实验设置三个方法：

| 方法 | 每轮完整场景块 | Farkas割 |
|---|---:|---:|
| 单块纯 CCG | 1 | 0 |
| Batch-4 CCG | 最多4 | 0 |
| Hybrid v7 | 最多4 | 1条哨兵割 |

所有方法使用相同实例、42个场景、成本锚点、成本容许比例、线程、种子、容差和最终完整分离认证。比较采用同批运行和交替顺序。

## 4. 算法贡献应如何定位

论文不能再把Olist速度优势归因于Benders哨兵割。准确表述应为：基于完整分离违反程度的有界批量场景提交，将多个关键场景一次性加入主问题，减少了主问题—分离循环，并在当前实例族上优于每轮只加入一个场景的标准CCG。

如果保留Hybrid框架，Farkas割仍可用于一般隐式不确定集中的可行性认证和候选筛选，但本次有限42场景实验没有证明割对速度有增量贡献。Olist实现的最快、最简版本是Batch-4 CCG，而不是带哨兵割的v7。

## 5. 对论文实验的影响

在冻结最终方法前不应重跑论文全部实验。现在需要先决定两种写法：

1. 将Batch-4 CCG作为真实数据扩展中的主要计算方法，并把原Hybrid作为一般框架；此时只需重跑涉及真实数据算法比较的实验。
2. 将批量场景提交整合进论文主算法；此时所有涉及Hybrid运行时间、迭代数、割数、场景块数、认证率和PAR-2的实验都必须统一重跑。

模型、数据、成本锚点、Direct模型规模、最优目标和管理结论不因调度策略变化而自动失效。运行时间不能跨批次拼接，正式表格必须重新采用同批配对。

## 6. 证据边界

这些Olist周已经用于v4至v7开发，属于观察过的开发实例。消融可以解释当前速度提升的来源，但不能替代新的独立确认实验。最终算法冻结后，仍需要在新数据、未观察时期或预先封存的新实例族上运行一次，才能把优势写成外部有效性证据。
