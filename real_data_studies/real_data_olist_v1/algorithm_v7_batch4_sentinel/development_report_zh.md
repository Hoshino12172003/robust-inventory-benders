# Hybrid v7 批量场景块与哨兵割：算法改进报告

## 1. 最终开发结论

Hybrid v7 在同一批次、交替运行顺序的12组 Olist 周度实例上达到了预先设定的内部成功标准。v7在12个实例上全部认证；纯 CCG认证11个实例。在双方均认证的11个实例上，v7逐例全部更快，平均时间由47.55秒降至32.24秒，下降32.21%，几何平均加速比为1.592。

该结果证明批量场景提升可以在当前实例族上优于每轮只加入一个场景块的纯 CCG。但是，v4至v7的设计过程已经观察过全部12个周，因此本结果属于算法开发证据，不能作为未接触留出集上的最终确认，也不能直接宣称普遍优于纯 CCG。

## 2. v7 的具体规则

v7保留名义场景和六个单因子场景对应的7个初始完整块。第一次主问题求解后，对其余35个场景执行完整固定场景分离，并按照Farkas违反程度排序。算法直接将前4个最严重场景加入为完整场景块，同时为最严重的未提升场景加入1条Farkas哨兵割。随后重新求解主问题并再次检查全部未加入场景。

若仍存在违反场景，算法重复“最多4个完整块加1条哨兵割”的操作；没有违反场景时才返回认证结果。由于每个未终止轮次至少加入一个先前不存在的完整场景块，且场景集合有限，算法保持有限终止性。Farkas割是有效不等式，批量加入完整块也不会排除任何鲁棒可行解，因此该改动不改变目标定义或正确性标准。

当前12个周度实例以及20/30城市开发实例均在2轮内完成。其最终主问题通常包含11个完整场景块和1条哨兵割；纯 CCG通常需要4至5轮才形成相近的完整块集合。

## 3. 为什么v4至v6仍然慢

v4先加入10条割，第二轮批量提升4个场景，但最终保留20条割。它虽然将迭代数从5降至3，却显著增加了困难公平主问题的单轮求解时间。

v5在场景提升后删除该场景对应的冗余割，将活动割从20条降至约16条。在11个双方成功周中，v5相对v4平均加速15.89%，但仍比纯 CCG慢32.45%，只有1周胜出。

v6把10条割全部视为临时探测割，提升场景后全部删除。开发实例有所改善，但首个困难周仍需128.86秒，而纯 CCG为108.12秒。原因是v6仍需先用一轮割探测，再在第三轮求解批量场景主问题；清理割没有消除额外求解轮次及求解路径差异。因此v6回放在两个周后停止，并保留为失败开发证据。

v7取消等待重复发现的探测轮，直接使用第一次完整分离已经得到的违反程度选择4个场景块，同时只保留1条割。这一修改同时控制了主问题规模和循环次数。

## 5. 正确性检查

v7在12个实例上均返回 `optimal` 并完成全部42个场景的最终分离认证。与完整42场景Gurobi Direct模型相比，v7目标值的最大绝对误差为1.10×10^-12，说明速度改善不是通过放宽目标、跳过场景或降低解质量获得的。

纯 CCG在5月21日实例上稳定返回 `uncertified_infeasible`。此前三次额外诊断均复现该状态；v7在同一实例上用约1.5秒完成认证。因此v7在当前实现下同时改善了认证率和运行时间分布。

## 6. 方法定位

v7并不是“通过修改数据让Hybrid获胜”。两种方法使用完全相同的实例、场景、成本锚点、成本容许比例、线程、种子、容差和求解器后端。唯一算法差异是每轮向主问题提交的场景块数量以及保留的Farkas割数量。

与纯 CCG相比，v7的实质贡献是违反程度驱动的批量场景提交；与纯批量CCG相比，v7额外保留一条未提升场景的Farkas哨兵割，因此仍属于场景块与Benders可行性割结合的Hybrid方法。论文中应把性能改善主要归因于有界批量场景块，而不能笼统归因于“使用Benders割”。

## 7. 仍需完成的独立确认

本轮开发已经耗尽现有Olist周度实例的独立性。若直接把11胜0负写成独立验证，审稿人可能质疑事后算法选择。论文采用v7前，应锁定当前代码哈希和全部设置，并在新的外部数据集、新的未观察时间段或事先生成且封存的新实例族上只运行一次。

新的确认实验必须同时报告所有实例、认证率、同批配对时间、目标误差、迭代数、场景块数和割数。若新数据未复现优势，应如实缩小结论范围，而不能继续在确认集上调参。
